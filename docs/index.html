N64 trig: S5C6 against the SM64 table

A sine/cosine kernel for the VR4300, measured in-game in HackerSM64 on ares v148. Source, data and how to reproduce: github.com/msmfai/N64-trig.

Emulator results only. Nothing here has been measured on a console. ares charges flat cache-miss costs and has no pipeline model; see the caveats at the end.

The kernel

S5C6 folds the angle to within 45° of the nearest quarter turn, then evaluates an odd degree-5 sine or an even degree-6 cosine. The two are fitted together, so the average of sin² + cos² − 1 over all 65536 angles is zero and they meet exactly at 45°. The two highest-order coefficients have only 8 significant bits, so each is built in the code with one lui. The other four fit in one 16-byte cache line. Cosine is trig_sin(angle + 0x4000): the add is exact, so it is bit-identical to a dedicated cosine.

How it was measured

A patched HackerSM64 plays SM64's seven attract-mode demos (4304 measured frames, about 440 sine/cosine calls per frame) and records the game's own profiler figure: game-thread CPU time per frame, with audio preemption excluded. Each kernel is built twice. In the table build, sins/coss stay table lookups, but the table is refilled from the kernel at boot. In the call build, every lookup calls the kernel. Both compute bit-identical values, so they play the same game; a hash of Mario's position checks that every frame. Each pair was built at three code layouts (0, 1024 and 4096 bytes of padding).

Layout matters more than the method. The swing comes from the I-cache. An inline table lookup is more code at each of the game's call sites than a jal, so the call builds take 40–1190 fewer I-cache misses per frame. How many fewer depends on where everything lands, so a single pair of builds can show either one winning.

This is the stable result. S5C6 is cheaper than Silas at every layout, because Silas's sine pays for a sqrt.s (about 29 cycles, against about 5 for a multiply).

What ares can't tell you

  • ares charges a flat 40 cycles per D-cache fill and write-back, and 48 per I-cache fill. On a console, fills compete with the RSP and RDP for RDRAM, so they can cost more during heavy rendering. Counting both caches, the call builds miss less than the table builds in every pair and layout here, so dearer misses would only move the result toward the kernels. By how much needs a console.
  • There is no pipeline model, and no early completion of simple multiplies, so instruction costs are approximate too.
  • Results were built with clang 21; HackerSM64's default gcc toolchain was not tested.
