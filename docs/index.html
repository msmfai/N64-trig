AI use: I'm a mathematician: I designed the approximation (the polynomial forms, the fit, truncating c and f to 8 bits, the constants in one cache line) and directed the work. Claude (Anthropic's AI) wrote the code, assembly, benchmark and report. No art, models or music.

A folded polynomial joint sine / cosine kernel for the N64 (VR4300), more than 10x more accurate than Silas Lock's. Source and raw data: github.com/msmfai/N64-trig.

It uses a polynomial approximation of

S(x) = x(a + x²(b + cx²))
C(x) = 1 + x²(d + x²(e + fx²))

instead of Silas's

C(x) = 1 + x²(a + bx²)
S(x) = √(1 − C(x)²)

and makes it inexpensive with the use of brackets you can see; by truncating c and f to 8 bit so they fit on one line of assembly; and putting the remaining constants into one cache line.

Three versions: one cache line, pure code, quantized

Same fold and polynomials; they differ only in how the six coefficients get into registers. The first two return the same values bit for bit; the third has its own coefficients.

Why there are three:

  • The cache-line version runs the fewest instructions, but only if its line is already in the data cache. If the game has evicted the line, the call waits for RAM (a cache miss).
  • The pure-code version can never miss on data. It costs 24 more bytes of instruction cache instead, and is one self-contained file with no .rodata to place or align.
  • The quantized version is pure code with only one lui + ori pair: 3 instructions shorter than the pure-code version. The price is accuracy: its s² + c² − 1 is 240x larger, which matters only where a rotation is applied again and again to its own result.
  • On ares the three are tied: the gaps are smaller than the ±3% that code layout alone moves results. ares charges a flat cost per miss and doesn't model RAM contention, so it can't say which one wins on a console.

Method

  • HackerSM64 at commit 3be00d2f, clang 21, US ROM. Times are HackerSM64's own profiler total: game-thread µs per frame, audio excluded, in emulated time.
  • Table build and call build: same values, same game; a hash of Mario's position over every frame checks it.
  • Calls cut the angle to the table's 4,096 steps, so all builds of one method give the same values.
  • 3 layouts: 0, 1024 and 4096 bytes of padding before the kernel.
  • Cache misses from ares's own counters via emux. ares charges 40 cycles per data miss or write-back, 48 per instruction miss, flat.
  • Rebuild: python3 bench/build.py --baserom sm64.us.z64 --variants kernels sincos, then python3 bench/run.py --variants kernels sincos.

# turn) for the N64 VR4300. Sine in $f0, cosine in $f2. Uses $t0-$t7 and
# $f0-$f16 only (all caller-saved). Max error 1.45e-5.
# S(x) = x(a + x^2(b + cx^2)), C(x) = 1 + x^2(d + x^2(e + fx^2)), x in +-1/8 turn.
# c (S5) and f (C6) are built with lui; a, b, d, e are one 16-byte cache line (trig_k).

    .set noreorder
    .set noat
    .text
    .global trig_sincos
    .type   trig_sincos, @function
    .balign 32
trig_sincos:
    addiu   $t0, $a0, 0x2000
    andi    $t1, $t0, 0x3fff
    addiu   $t1, $t1, -0x2000        # x: offset from nearest quarter turn
    mtc1    $t1, $f0
    lui     $t7, %hi(trig_k)
    lui     $t3, 0x1a97              # S5 =  6.245213624775359e-23
    cvt.s.w $f0, $f0
    addiu   $t7, $t7, %lo(trig_k)
    mtc1    $t3, $f4
    lui     $t3, 0x925d              # C6 = -6.973530402153744e-28
    mul.s   $f2, $f0, $f0            # x2
    mtc1    $t3, $f12
    lwc1    $f6, 4($t7)              # S3
    lwc1    $f14, 12($t7)            # C4
    lwc1    $f8, 0($t7)              # S1
    lwc1    $f16, 8($t7)             # C2
    mul.s   $f4, $f4, $f2
    lui     $t6, 0x3f80              # 1.0
    mul.s   $f12, $f12, $f2

    add.s   $f4, $f4, $f6

    mul.s   $f12, $f12, $f2

/* kernel/sincos.h */
#ifndef SINCOS_H
#define SINCOS_H

/* Sine and cosine of one angle in one call: kernel/sincos.s or sincos_code.s.
 * GNU C returns _Complex float in $f0/$f2, so nothing goes through memory.
 * sincoss(a, s, c) sets s = sins(a), c = coss(a). */
_Complex float trig_sincos(int angle);
#define sincoss(x, s, c) do { _Complex float _sc = trig_sincos((unsigned short) (x)); \
    (s) = __real__ _sc; (c) = __imag__ _sc; } while (0)

#endif
S5C6 line: trig_sin and trig_sincos (kernel/s5c6.s) 
# float trig_sin(int angle)  -- S5C6 sine/cosine kernel for the VR4300 (N64)
#
# angle: SM64/MM binary angle in $a0 (0x10000 = one turn; only bits 0-15 used)
# result: sine in $f0.  For cosine call trig_sin(angle + 0x4000): the add is
#         exact, so cosine is bit-identical to a dedicated cosine routine.
#
# Fold: t = angle + 0x2000; x = (t & 0x3FFF) - 0x2000 is the offset from the
# nearest quarter turn (|x| <= 0x2000 = 45 degrees). Bit 14 of t selects the
# cosine polynomial, bit 15 of t negates the result. (Folding idea: Silas Lock.)
#
#   sin = x * (S1 + x2*(S3 + S5*x2))
#   cos = 1 + x2*(C2 + x2*(C4 + C6*x2))        x2 = x*x, x in binary-angle units
#
# Sine and cosine are fitted jointly: the average of sin^2 + cos^2 - 1 over all
# angles is pinned to zero (so bone chains don't grow or shrink), and the two
# polynomials agree exactly at 45 degrees (sine is exactly odd).
# S5 and C6 have only 8 significant bits (low 16 bits zero), so each is built
# with one lui; the other four are loaded from one 16-byte cache line (trig_k,
# in s5c6.c). Coefficients: BFS_* in fit/coeffs.h, made by fit/fit.py.
#
# GNU as syntax (o32). Assemble as a .s file; mips-linux-gnu-gcc -c works.
#
# Leaf function, no stack, caller-saved registers only. Hazards respected:
# one instruction between mtc1 and use, no back-to-back mul.s, no mul.s in a
# branch delay slot (VR4300 multiply erratum).

    .set noreorder
    .set noat
    .text
    .global trig_sin
    .type   trig_sin, @function
    .balign 32
trig_sin:
    addiu   $t0, $a0, 0x2000
    andi    $t1, $t0, 0x3fff
    addiu   $t1, $t1, -0x2000        # x
    mtc1    $t1, $f0
    andi    $t2, $t0, 0x4000         # cosine octants?
    lui     $t7, %hi(trig_k)
    cvt.s.w $f0, $f0                 # x as float
    addiu   $t7, $t7, %lo(trig_k)
    mul.s   $f2, $f0, $f0            # x2
    bnez    $t2, 1f
    andi    $t5, $t0, 0x8000         # negate? (delay slot)

# sine octants: x * (S1 + x2*(S3 + S5*x2))
    lui     $t3, 0x1a97              # S5 = 0x1a970000 (8 significant bits)
    mtc1    $t3, $f4
    lwc1    $f6, 4($t7)              # S3
    lwc1    $f8, 0($t7)              # S1
    mul.s   $f4, $f4, $f2
    add.s   $f4, $f4, $f6
    mul.s   $f4, $f4, $f2
    add.s   $f4, $f4, $f8
    mul.s   $f0, $f4, $f0
    bnez    $t5, 3f
    nop
    jr      $ra
    nop

# cosine octants: 1 + x2*(C2 + x2*(C4 + C6*x2))
1:  lui     $t3, 0x925d              # C6 = 0x925d0000 (8 significant bits)
    mtc1    $t3, $f4
    lwc1    $f6, 12($t7)             # C4
    lwc1    $f8, 8($t7)              # C2
    lui     $t6, 0x3f80              # 1.0
    mul.s   $f4, $f4, $f2
    mtc1    $t6, $f10
    add.s   $f4, $f4, $f6
    mul.s   $f4, $f4, $f2
    add.s   $f4, $f4, $f8
    mul.s   $f4, $f4, $f2
    add.s   $f0, $f4, $f10
    bnez    $t5, 3f
    nop
    jr      $ra
    nop

3:  jr      $ra
    neg.s   $f0, $f0                 # (delay slot)

    .size   trig_sin, . - trig_sin

/* The four full-precision S5C6 coefficients, read by s5c6.s: one 16-byte,
 * 16-byte-aligned cache line. S5 and C6 are built in the code (lui). */
typedef struct {
    float s1, s3, c2, c4;
} TrigK;

const TrigK trig_k __attribute__((aligned(16))) = {
     9.586999658495188e-05f,   /* S1  0x38c90dd0 */
    -1.4654559033280834e-13f,  /* S3  0xaa24fee4 */
    -4.595529734530146e-09f,   /* C2  0xb19de6b5 */
     3.4901736165623554e-18f,  /* C4  0x2280c3c2 */
};

# LUTX16: node i = (|x| + 256) >> 9, d = |x| - i*512, node = 32 bytes:
#   sine line   S, C*M, S*K*M^2 -> s = S + (d*CM - d2*SKM2)
#   cosine line C, S*M, C*K*M^2 -> c = C - (d*SM + d2*CKM2)
# The sine value is odd in x: negate when x < 0 differs from bit 15 of t.
    addiu   $t0, $a0, 0x2000
    andi    $t1, $t0, 0x3fff
    addiu   $t1, $t1, -0x2000        # x
    sra     $t7, $t1, 31             # 0 or -1
    xor     $t1, $t1, $t7
    subu    $t1, $t1, $t7            # |x|
    addiu   $t8, $t1, 256
    sra     $t8, $t8, 9              # i
    sll     $t9, $t8, 9
    subu    $t9, $t1, $t9            # d
    mtc1    $t9, $f0
    sll     $t8, $t8, 5
    lui     $t3, %hi(gTrigLutx16)

# on bit 15 ^ (x < 0); cos = the cosine line, negated on bit 15. Odd: sin =
# the cosine line, negated on bit 15; cos = the sine line, negated on
# !bit 15 ^ (x < 0).

    mtc1    $t9, $f0
    sll     $t8, $t8, 5
    lui     $t3, %hi(gTrigLutx16)
    addiu   $t3, $t3, %lo(gTrigLutx16)
    cvt.s.w $f0, $f0                 # d

    lwc1    $f6, 4($t3)              # CM
    lwc1    $f14, 20($t3)            # SM

    mul.s   $f6, $f0, $f6

Glossary

vanilla table
SM64's sine table: 5,120 floats (20 KB), sine and cosine sharing it. A lookup is gSineTable[angle >> 4], about 4 inline instructions, 4,096 steps per turn.
binary angle
SM64's angle unit: 0x10000 is one turn, 0x4000 a quarter.
fold
For a binary angle: t = angle + 0x2000; x = (t & 0x3FFF) − 0x2000 is the offset from the nearest quarter turn (at most 45°). Bit 14 of t picks the sine or cosine polynomial, bit 15 negates. Idea from Silas Lock.
S5C6
This repo's method: on the fold, sine = x(a + bx² + cx⁴) (degree 5) and cosine = 1 + x²(d + ex² + fx⁴) (degree 6), fitted together so sin² + cos² stays 1 on average and both meet exactly at 45°. c and f have 8 significant bits, so each loads with one instruction.
line
S5C6 variant: the four full-precision coefficients are read from one 16-byte data cache line.
code
S5C6 variant: every coefficient is built in instructions; no data at all.
Silas
Silas Lock's folded polynomial (github.com/AdamPrimer/folded-polynomial): cosine = 1 + x²(K1 + K2x²) on the fold, sine = √(1 − cos²) with one sqrt.s.
LUTX16
A 16-segment table with quadratic interpolation: 17 nodes of 32 bytes (544 B), each holding the sine and cosine value and slope terms.
sincos
One call returning sine and cosine of one angle. The fold and the constants are shared and the two polynomials interleave, so it costs less than two calls.
table build / call build
A table build fills the vanilla table from the kernel at boot and keeps table lookups; the call build calls the kernel. Same values, so the same game; the difference is only the cost.
layout
Where code sits in memory. Padding before the kernel moves it and everything after it, which changes which code shares cache lines. It moves results by about ±3%.
cache miss
The VR4300 has a 16 KB instruction cache (32-byte lines) and an 8 KB data cache (16-byte lines). A miss loads a line from RAM. An inline table lookup is more code than a call, so calls can save instruction misses.
max error
Largest difference from the true sine over all 65,536 angles.
µs/frame
Game-thread CPU time per frame. SM64 runs at 30 fps: 33,333 µs per frame. The game thread uses about 12,300.
VR4300
The N64's CPU, 93.75 MHz MIPS III with an FPU.
VR4300 multiply erratum
On early CPUs a mul.s or mul.d directly followed by another multiply can give a wrong result. Compilers work around it with -mfix4300; the kernels avoid the pattern.
ares
A cycle-counting N64 emulator (ares-emu.net). Deterministic: the same ROM gives the same cycle count every run.
emux
ares's extension instructions, available in Homebrew Mode: the ROM reads cache counters, prints results and quits ares.
HackerSM64
A Super Mario 64 decompilation fork for ROM hacks (github.com/HackerN64/HackerSM64), with a built-in profiler.
IDO
SGI's compiler, used by the original game and the matching decompilation.

Fold: Silas Lock. Written with AI assistance (Claude). MIT. No ROMs distributed.
